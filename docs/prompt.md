# mini-llmcache 验证与性能优化任务书

## 1. 目标

对 mini-llmcache（约 870 行的 LMCache 教学版）完成三件事：

1. 正确性验证：模型加载、推理、缓存读写全链路正确，包含跨重启的 L2 磁盘持久化。
2. 基准测试：在多个模型和配置下测量 prefill 加速，找出规律和瓶颈。
3. 代码优化：在保证正确性的前提下，把缓存加速能力做到最大。

## 3. 正确性验收

| 检查项 | 验收标准 | 手段 |
|---|---|---|
| 模型加载 | vLLM 启动成功，server 打印 `REGISTER ... (chunk=.. MiB, N engines)` | 日志 |
| 推理正确 | HTTP 200，输出合理 | `curl` |
| 缓存写入 | 第一遍请求后 server 打印 `STORE tokens [...]` | 日志 |
| 缓存命中 | 第二遍同 prompt 时 server 打印 `RETRIEVE hit L1=N`，且输出与冷启动逐字节一致 | 日志 + 输出比对 |
| L2 持久化 | 杀掉 server 和 vLLM，重启后再次请求：`RETRIEVE hit L1=0 L2=N`，延迟接近热命中 | 日志 + 计时 |
| 单元测试 | `python -m pytest tests/` 全绿（当前 50 个） | pytest |

## 4. 基准测试口径

### 4.1 指标

- 主指标：TTFT（首 token 延迟）。
- 次指标：吞吐加速，重点看共享前缀场景下的总墙钟。
- 加速比统一定义为 `cold / hot`。
- 每次正式测试前都要清空 server 和 L2：`rm -rf /tmp/mini-l2`。
- 先做一个短 prompt warmup，不计入结果。
- `temperature=0`，便于逐字节比对输出。

### 4.2 数据集场景

| 场景 | 构造 | 关注点 |
|---|---|---|
| 完全重复 | 同一长 prompt x2 | 全命中加速、输出一致性 |
| 共享前缀 | 1 个长前缀 + 4 个不同后缀 | 部分命中加速 |
| 无复用 | 4 条不同等长 prompt | 冷启动基线 |
| SQuAD 式 100 条 | 20 上下文 x 5 问（优先 HF 下载，离线则本地构造） | 真实问答形态下的命中率与吞吐 |
| 吞吐 | N 条请求共享同一前缀 | 前缀复用场景的总吞吐 |

### 4.3 配置矩阵

| 维度 | 取值 |
|---|---|
| 模型 | 0.6B / 8B / 32B（TP=2、TP=4、TP=8） |
| chunk-size | 64 / 128 / 256 / 512 / 1024 |
| L1 大小 | 4 / 8 / 16 / 32 GB |
| L2 大小 | 4 / 8 / 16 / 32 / 64 / 128 GB |
| prompt 长度 | 1024 / 2048 / 4096 / 8192 / 16384 / 32768 token |

脚本：

- `benchmarks/bench.py`：单配置场景选择
- `benchmarks/sweep.py`：自动扫 chunk x L1
- `benchmarks/probe.py`：直连服务器测 LOOKUP / RETRIEVE 裸耗时

## 5. 当前结果与瓶颈（截至 2026-08-19）

### 5.1 已测数据

| 模型 | 场景 | 冷 TTFT | 热 TTFT | 加速 | 关键证据 |
|---|---|---|---|---|---|
| 0.6B | 完全重复 3072t | 0.41s | 0.53s | 0.8x | 命中 11/11，输出一致；100 条命中率 100% 但 TTFT 仍为 0.8x |
| 8B | 完全重复 3072t | 0.63s | 0.74s | 0.9x | 命中 11/11，输出一致 |
| 32B（TP2） | 完全重复 3072t | 0.80s | 0.81s | 1.0x | 命中 10-11/11，输出一致 |
| 32B（TP2） | 吞吐（20 x 共享前缀） | 3.04s（总） | - | 1.0x | 全部命中，但全部走 L2 |
| 32B 探针 | LOOKUP resolve | 0.4ms（L1 热）/ 106ms（L2） |  |  |  |
| 32B 探针 | RETRIEVE 336MB 往返 | 290ms -> 251ms（调 SNDBUF/RCVBUF） |  |  | 零拷贝直发已实现，待复测 |

### 5.2 主要瓶颈

1. 预取临时条目“用完即弃”：从 L2 拉回的块在 RETRIEVE 后立即释放，导致共享前缀的每个请求都重新走一遍 L2 -> L1。修复方向：RETRIEVE 消费后转常驻，交给 LRU 淘汰。
2. TTFT 被 decode 稀释：32B 单 token decode 约 125ms，首 token 前的固定成本会吃掉 prefill 节省。
3. warm 路径串行：LOOKUP -> RETRIEVE -> H2D 回填 -> 后缀 prefill，vLLM 等待期间没有计算重叠。
4. 小模型 prefill 太便宜：0.6B 3072t 约 0.35s，传输开销和收益同量级。

### 6.1 8B 全矩阵结果（chunk x L1，TTFT 口径）

| chunk | L1=4GB | L1=8GB | L1=16GB |
|---|---|---|---|
| 128 | 0.91x | **0.98x** | 0.86x |
| 256 | 0.95x | 0.93x | 0.95x |
| 512 | 0.87x | 0.86x | 0.88x |
| 1024 | 0.72x | 0.93x | 0.91x |

结论：8B 的 12 个配置全部小于 1x（0.72x - 0.98x），说明该模型的 prefill 太便宜，任何 chunk / L1 组合都难以覆盖传输成本。当前最优是 chunk=128、L1=8GB，最差是 chunk=1024、L1=4GB。

### 6.2 32B 全矩阵结果（TP=2）

| chunk | L1=8GB | L1=16GB |
|---|---|---|
| 128 | 0.66x | 1.08x |
| 256 | **1.36x** | 1.17x |
| 512 | 1.21x | 0.95x |
| 1024 | 1.25x | 0.81x |

规律：

- **最优配置：chunk=256、L1=8GB（TTFT 加速 1.36x）**。
- chunk=256 明显优于 128，说明更小的 chunk 会让 RETRIEVE 帧数翻倍，传输开销增加；512/1024 命中粒度变粗，部分命中场景收益下降。
- L1=8GB 全面优于 16GB（大池驻留更多条目后 eviction 与预取交互更频繁）。
- 与 8B 全部 < 1x 不同，32B 上 chunk=256 已经稳定 > 1x，说明大模型的 prefill 成本终于盖过了传输开销。

注：chunk-size 必须 >= 128 且是 128 的倍数（vllm-ascend block_size=128），64 不可行。

### 6.3 最优配置（chunk=256，L1=8GB）32B 完整五场景验证

| 场景 | 冷 TTFT | 热 TTFT | 加速 | 关键证据 |
|---|---|---|---|---|
| 1 完全重复 3072t | 0.633s | 0.585s | 1.1x | 11/11 L1 命中，输出逐字节一致 |
| 2 共享前缀 3072t | 0.597s | 0.526s | 1.1x | 10/10 L1 命中 |
| 3 无复用基线 | 0.570s 平均 | - | - | 冷启动参考 |
| 4 100 条 SQuAD | 0.202s | 0.298s | 0.72x | 命中率 80/80（100%）；短上下文（1KB）传输主导 |
| 5 吞吐 20 请求 | 0.986s | 0.60s | **1.6x TTFT / 1.2x 墙钟** | 全部 L1 命中 |

验证结论：

- 中等前缀（3072t）场景 1.1x、吞吐场景 1.6x——最优配置下稳定 > 1x；
- 短上下文（场景 4，约 1KB）仍 < 1x（传输主导，与 5.2 瓶颈 2 一致）；
- 收益随前缀长度上升，在共享前缀的批量场景最大化。

## 7. 优化优先级

1. 临时条目转常驻：预取从 L2 拉回的块被 RETRIEVE 消费后保留在 L1，而不是立即释放。
2. 降低传输开销：继续排查 pickle 头、ZMQ 帧数、零拷贝路径。
3. 流水线重叠：让 RETRIEVE 的 H2D 回填与未命中部分的 prefill 并行。
4. chunk-size 扫描：128 / 256 / 512 / 1024 x 长 prompt，找传输量与命中粒度的平衡点。

每一步优化后都要满足：

- `python -m pytest tests/` 50 个用例全绿；
- 干净环境重跑基准；
- 输出可复现的加速数据。
